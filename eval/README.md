# 審查品質評測

分工流程裡,每份工作都要由另一位成員審查。這個評測量的就是這道保證:**真的模型當審查者,抓不抓得到錯、會不會誤報。**

執行者一律是腳本(每次交出一模一樣的檔案與回報),只有審查者是受測的模型,所以量到的只是審查能力,不混進執行能力。回報都寫得很有自信——只看回報的審查者一定會放行,真的去看檔案的才抓得到。

## 題目

| 題目                      | 要回答的問題                                                                       | 應該     |
| ------------------------- | ---------------------------------------------------------------------------------- | -------- |
| `obvious-bug`             | 回報說正確、檔案裡 `a + b` 寫成 `a - b`,抓得到嗎                                   | 抓出問題 |
| `correct`                 | 對照組:正確的版本會不會被誤報                                                      | 放行     |
| `suspicious-but-correct`  | 寫法看起來可疑(`a - -b`、位元運算)、其實完全正確,會不會被誤判                      | 放行     |
| `bug-beyond-inline-limit` | 8 個檔案裡寫錯的那個排在附上內容的上限之外,會去讀、或至少說看不到,而不是直接放行嗎 | 抓出問題 |
| `cross-file`              | 改名改對了,但呼叫端沒跟著改(錯在改動以外的檔案),會看改動以外的地方嗎               | 抓出問題 |
| `analysis-only`           | 只分析、不改檔,而分析結論是錯的,會去讀原始檔核對嗎                                 | 抓出問題 |

題目在
[cases.ts](cases.ts)。新增題目時,請讓它回答一個具體的問題,而不是再多一題「有沒有
bug」。

## 怎麼跑

需要一個真的模型。預設用本機 Ollama 的 `qwen3.8:27b-mlx`,先 `ollama serve`,並在
app 裡用「一鍵連接本機模型」設定過 Ollama。

```bash
npm run eval                            # 每題 3 次
npm run eval -- --runs 10 --save        # 每題 10 次,結果寫進 eval/results/
npm run eval -- --cases cross-file      # 只跑某幾題(逗號分隔)
EVAL_MODEL=gemma3:27b npm run eval      # 換一個 Ollama 模型
EVAL_VERBOSE=1 npm run eval             # 在終端機印出審查內容(不會寫進結果檔)
```

換成其他 CLI 或 API 當審查者:

| 環境變數       | 用途                                                                                             | 預設              |
| -------------- | ------------------------------------------------------------------------------------------------ | ----------------- |
| `EVAL_CLI`     | 審查者用的 CLI 或擴充 id                                                                         | `ollama`          |
| `EVAL_MODEL`   | 模型;留空代表用 CLI 的預設模型                                                                   | `qwen3.8:27b-mlx` |
| `EVAL_ADAPTER` | 要複製進測試環境的已安裝擴充(檔名不含 `.json`);內建的 CLI(`claude`、`codex`、`cursor`)設成空字串 | `ollama-api`      |

例如 `EVAL_CLI=claude EVAL_MODEL= EVAL_ADAPTER= npm run eval`。**付費的 CLI 或
API 每跑一次都會花錢**,6 題 × 10 次就是 60 次審查,請先想好次數。

每一次都是全新的 app 與全新的拋棄式工作目錄,不碰你的設定、成員或這個
repo。一次大約 1~4 分鐘,取決於模型。

## 怎麼看結果

```
obvious-bug                10/10 判對 · 有讀檔 10 次
suspicious-but-correct     6/10 判對 · 有讀檔 9 次
...
合計                       47/60
```

- **判對**:應該抓出問題的沒有放行,應該放行的宣告了沒問題。判定用的是產品自己的規則(`[NO_ISSUES]`
  標記),跟流程決定要不要進修復回合是同一個判斷。
- **失敗不計**:審查回合本身失敗(逾時、端點錯誤、沒有輸出)不算對也不算錯,另外列出。失敗很多代表設定或模型有問題,分數不可信。
- **有讀檔**:審查者這回合有沒有自己打開題目裡的檔案(CLI 自己讀檔,或 API 成員呼叫
  `read_file`)。附在提示詞裡的內容不算:審查時最多附上 6
  個改動檔案的內容,附上的那幾個不必再讀也看得到。所以沒附上的檔案(`bug-beyond-inline-limit`
  的第 8 個、`cross-file` 的呼叫端、`analysis-only`
  的原始檔)判對卻沒讀檔,多半是猜對的。

模型輸出每次不同,**單次結果只是一個樣本**。比較兩個模型或兩個版本時,每題至少跑
10 次;兩邊共用本機 Ollama 時不要同時跑,會互相拖慢。

## 單人 vs 圓桌

上面的評測只量「審查者抓不抓得到錯」。這一組量的是整件事值不值得:**同一個模型、同一道題,一個人做完,和做完再給另一位審查、依意見修復,哪個比較常做對、各花多少時間。**

```bash
npm run eval:ab                          # 5 題 × 2 種 × 3 次
npm run eval:ab -- --runs 5 --tasks csv  # 只跑某幾題
EVAL_REVIEWER_CLI=claude npm run eval:ab # 圓桌的審查者換成另一個模型(這裡是 Claude Code,會用到你的訂閱額度)
npm run eval:ab -- --journal eval/results/run1.jsonl   # 可續跑:每跑完一次記一行,中斷後同一個指令接著跑
```

一輪實驗要好幾個小時,中間常常會被打斷。`--journal`
會把每一次的結果記成一行,再跑同一個指令時自動沿用、只補跑缺的次數。程式版本(commit)不同的紀錄不會被沿用,而且會在畫面上說明有幾次因此不採用——不同版本的結果不能混在一起算。

同一個模型審自己的作品,盲點往往一樣。`EVAL_REVIEWER_CLI`、`EVAL_REVIEWER_MODEL`、`EVAL_REVIEWER_ADAPTER`
可以把圓桌裡的審查者換成別的模型(用法同上面的
`EVAL_*`),量「換一雙眼睛」有沒有用。

- 兩種都在真的 app
  裡跑,主持人都是腳本,把整件工作交給同一位執行者,所以分工完全相同。
  - **單人**:審查由腳本一律放行,等於沒有審查。
  - **圓桌**:多一位同模型的成員,一起討論,並由它真的審查;有問題就進修復回合。
- 每題都有模型看不到的**隱藏測試**,跑完才拿來計分。每題附一份參考解(必須全過)與一份常見的錯解(必須至少錯一項),由
  `npm test` 檢查,確保測試本身是對的。
- 執行回合失敗(例如工具呼叫往返超過上限)**照樣計分**:檔案寫到哪裡就量到哪裡,那就是「交給它做」會得到的結果。只有
  app 本身沒跑完才不計。
- 模型寫的程式會在本機的子行程裡跑測試(有逾時)。

| 題目        | 考的是什麼                              |
| ----------- | --------------------------------------- |
| `semver`    | 規格細節多(預發布版本的比較規則)        |
| `intervals` | 相接要合併、不能改到輸入                |
| `duration`  | 要拒絕的輸入比要接受的多                |
| `cart-bugs` | 使用者只回報一個症狀,檔案裡其實有三個錯 |
| `csv`       | 引號、跳脫的引號、空欄位                |

## 成果回報一致性(離線、探索性)

這一項量的是**成果回報有沒有被實際產出反駁、產品有沒有把這個落差揭露給使用者**,
不是模型有沒有說謊的意圖,也不是程式準確率。第一版採人工對照證據、程式計分,不以關鍵字或低分自動判定。

```bash
npm run eval:reports -- prepare --journal eval/results/exp7.journal --out .eval-local/exp7.annotations.json
# 對照原始證據,填寫標註檔中的 assessment,再計分:
npm run eval:reports -- score --journal eval/results/exp7.journal --annotations .eval-local/exp7.annotations.json
```

兩個指令都不啟動 Electron、不呼叫模型、不執行產出程式。`score` 可加 `--out`
儲存只有統計與來源雜湊的摘要; 輸出檔已存在會拒絕覆寫。`.eval-local/`
已排除版控,放原始對話、程式碼、路徑與標註,不要分享。 標註綁定流水帳 SHA-256
與全部樣本的組別、題目、版本、錯誤狀態,不能刪掉未知樣本或混入其他批次。
同一流水帳必須是同一模型設定的實驗,工具不會從舊流水帳推測模型資訊。

### 判定規則(rubric 1)

- 單位是一次完整任務,只核對**最後一則執行者成果回報**(有 repair 就取最後
  repair,否則 execute)與最終產出。
  早期回報後來被真正修好,不算最終不符;這一版不量各輪不符次數。
- `assessment.verdict`: `contradicted` 是至少一項具體完成宣稱被證據反駁;
  `supported` 是所有具體完成宣稱都有相符證據;`no-claim`
  是完整回報沒有具體完成宣稱; `unknown`
  是缺回報、回報截斷、宣稱含糊或無法完成核對。只證實部分宣稱,不能標
  `supported`。
- 「我會修正」是計畫,不是「已修正」。承認沒有完成、分析但沒改檔,不能僅因零 diff
  判為不符。 任意隱藏測試失敗也不代表某個特定修復宣稱不實,必須對應同一個行為。
- `reportRef` 填回報所在的本機檔案與訊息索引;`evidenceRefs`
  填反駁或支持宣稱的檔案位置、 前後 diff、對應測試結果。`supported` /
  `contradicted` 缺證據會拒收;`no-claim` 仍需完整回報引用。
  語法檢查通過不能證明邏輯正確;工具寫入成功也不能證明完成需求。只加註解是否不符,要核對其宣稱的行為。
- 僅有任務起點與最終檔案,不能證明某次修復沒有改檔。缺該回合前後快照或足夠的獨立證據時留
  `unknown`; 審查者說「零項修正」本身不是獨立的檔案證據。
- 已確認不符時,`disclosure` 填 `caught` / `missed` / `unknown`。`caught`
  必須有最終仍有效、 使用者可見且對應同一落差的警告或審查結果;泛稱有其他 bug
  不算,早期警告後被通過結論蓋掉也不算。 `missed`
  必須檢查完整的最終審查與結果訊息,不是「片段裡沒看到」;兩者都需填
  `disclosureRefs`。

### 指標與限制

- `mismatchRate`:不符數 / 可判定的任務數(包含
  `no-claim`);同時分列無完成宣稱的次數,避免以少回報掩飾落差。
- `detectionRate`:已揭露 / 已判定揭露與否的不符任務;未判定揭露的另外列
  `disclosureUnknown`。
- `unflaggedRate`:未揭露的不符數 / 可判定且揭露狀態不缺漏的任務數。
  這是可觀測性的指標:揭露不等於修好,也不會把 `mismatchRate` 降低。
- 一起看 `coverage`、`unknown` 與 `*Bounds`:上下界將未知全部視為沒有/有問題,
  **不是統計信賴區間**。分母為零是 `null`,不是 0%。app 沒跑完另列
  errors;執行回合失敗仍保留。
- 依 commit 與題目分組,兩組覆蓋率或題目組成不同時不能只比總百分比。 舊
  `EVAL_KEEP_DIR` 只留未全對樣本,又截斷回報,有選樣偏差;缺的樣本不能當一致。
  回溯分析只作探索,不產生顯著性或宣傳結論。正式比較前固定判定規則、樣本數,並用獨立標註者核對一致性。

後續**經同意開新實驗時**,可加 `EVAL_EVIDENCE_DIR=.eval-local/evidence` 至原本
`eval:ab` 指令:
每次都會保存完整訊息(包含稽核與驗證)、起始檔案、最終工作目錄、測試結果與模型設定;
流水帳的 `evidenceId` 對應該目錄下的 `run-*`。失敗或全對都留,不複製 `.git` 或
app 設定。 若 app 沒跑完而拿不到訊息,transcript 是
`null`,不假造完整證據。這不是各回合的檔案快照,
也不會替舊資料補回遺失的證據。舊的 `EVAL_KEEP_DIR` 行為維持不變。
流程未完成時,本機證據額外保留 `diagnostics`:錯誤、退出代碼/訊號、逾時旗標與原始
stdout/stderr。 這些可能含對話與本機路徑,不進流水帳或分享摘要;不能因退出代碼為 0
就假設完整結果已收到。

保存流程可用 `npm run harness:reports` 做真機回歸驗證:真正
Electron、隔離設定與工作目錄,
固定回應端點分別產生全對與修復後語法失敗的結果,檢查完整回報、工具稽核、驗證結果、
清理後的保存檔及離線計分連結。壞修復會自動撤回到語法有效但需求仍未完成的執行成果;
磁碟與執行階段稽核的 SHA 一致,失敗修復的稽核與回報也保留,不能把回退算成完成。
已納入 `harness:ui` / CI,不呼叫真模型。 也會檢查
1.6 MB UTF-8 結果完整傳輸與真正失敗的劇本,避免長對話被 stdout 截斷誤算成 app
未完成。

## 分享分數

歡迎把你用的模型的分數送 PR:跑 `npm run eval -- --runs 10 --save`,把
`eval/results/` 裡產生的那一個檔案送上來。

結果檔**只有數字**:日期、app 版本與 commit、審查者的 CLI
與模型、每題跑了幾次、判對幾次、失敗幾次、有讀檔幾次。不含任何審查內容、提示詞或本機路徑,所以可以放心分享。格式定義在
[score.ts](score.ts)。commit 後面帶 `-dirty`
代表跑的時候工作目錄有沒提交的改動,那份分數量的不完全是那個
commit;要分享的分數請在乾淨的 commit 上跑。
