# 實驗紀錄

評測的每一次正式實驗都記在這裡:**開跑前**先寫下假設、指標、次數與判斷標準,跑完照實填上結果,不因為結果回頭改前面的設定。沒有照這個流程跑的結果只算探索,不當結論。

共通設定:本機 Ollama 的 `qwen3.8:27b-mlx`,主持人是腳本(兩種條件的分工完全相同),只有「app 本身沒跑完」的次數不計分。統計方法見 [stats.ts](stats.ts)。

## 實驗 1:舊流程、基本題組(探索)

- 日期:2026-09-19;程式:`f89a08c` 之後、審查流程改動之前
- 題目:基本題組 5 題 × 單人 / 圓桌 × 3 次
- 結果:全對 單人 12/15、圓桌 11/14;Fisher 精確檢定 p = 1.00
- 時間:圓桌平均慢約 1.5–3 倍
- 結論:**量不出差別。** 事後的檢定力計算:要偵測「80% → 95%」每組約需 76 次,3 次只抓得到非常大的差距。
- 過程中發現並修正的問題:
  - 第一版題目只寫「以 module.exports 匯出」,模型把函式本身指定給 module.exports,邏輯全對卻 0 分。量到的是題目的歧義,那一輪作廢重跑。
  - 執行回合中途失敗、檔案寫到一半時,流程跳過審查;修復後也不再審查。這兩個漏洞促成了實驗 2 的流程改動。

## 實驗 2:新流程(失敗照樣送審、修復後複查、逐條對照需求)、基本題組(探索)

- 日期:2026-09-19
- 題目:同實驗 1
- 結果:**中途停止**,只跑完 semver 的 5 次:單人 10/10、10/10、10/10;圓桌 10/10、9/10(有修復與複查,花了 18 分鐘)
- 停止的理由:檢定力計算顯示,基本題組每種 3 次不可能得出結論(Qwen 單人在這組題目已接近滿分)。把機器時間留給預先登記的實驗 3。
- 定位:探索,不下結論。

## 實驗 3:新流程、難題組(預先登記)

**假設 H1**:同一個模型當執行者與審查者時,圓桌(新流程)每次的測試通過比例高於單人。

- 題目:難題組(`cron`、`pathnorm`、`roman`、`lru-ttl`),依下面的校準決定納入哪些
- 校準(開跑前):單人各跑 3 次。單人全對率落在大約 20%–80% 的題目才納入;太容易或太難的剔除,並在這裡記下。
- 校準結果(2026-09-19,單人,只有這些資料,還沒有任何圓桌的數據):

  | 題目 | 單人全對 | 測試通過比例 | 沒過的項目 |
  | --- | --- | --- | --- |
  | cron | 2/3 | 99% | 日與星期都有限制、都不符合時誤判成符合 |
  | pathnorm | 0/3 | 84% | 相對路徑開頭的 `..` 被丟掉、`./` 的結尾斜線、根目錄的 `..` |
  | roman | 2/3 | 96% | 一次把轉回整數整個寫壞 |
  | lru-ttl | 3/3 | 100% | — |

  沒過的都是真的邏輯錯(逐項對照過保留的檔案),不是測試或題目的問題。
- **納入規則的修正**(開跑正式實驗之前):原規則用「全對率」判斷,會把 pathnorm 剔除(0/3)。但主要指標是「測試通過比例」,pathnorm 在主要指標上反而最有進步空間(84%)。原規則用錯了指標,改成:**單人的測試通過比例沒有滿分、也不是全錯,就納入**。修正只用到上面的單人校準資料。
- 納入:`cron`、`pathnorm`、`roman`;剔除:`lru-ttl`(單人已滿分,量不出差別)
- 程式版本:`b2db33c` 之後尚未提交的改動(審查流程、評測),結果檔的 commit 會標 `-dirty`
- 次數:每題每種條件 **8 次**(固定次數,中途不看結果決定要不要停)
- 主要指標:每次的測試通過比例。檢定:依題目分層的置換檢定,雙尾,α = 0.05
- 次要指標:全對率(Fisher 精確檢定)、平均時間
- 判斷:p < 0.05 且差距為正,才說「圓桌比單人準」;p ≥ 0.05 就報告「量不出差別」,連同信賴區間
- 結果(2026-09-20 跑完,48 次全部跑完,沒有「app 沒跑完」而不計分的):

  | 題目 | 單人:全對 / 測試通過 / 平均時間 | 圓桌:全對 / 測試通過 / 平均時間 |
  | --- | --- | --- |
  | cron | 4/8 · 86% · 522 秒 | 5/8 · 77% · 569 秒 |
  | pathnorm | 3/8 · 93% · 212 秒 | 1/8 · 90% · 415 秒 |
  | roman | 7/8 · 99% · 255 秒 | 8/8 · 100% · 485 秒 |
  | 合計 | 14/24(95% 信賴區間 39%–76%) | 14/24(39%–76%) |

  - 主要指標:圓桌 − 單人 = **−3.8 個百分點**,分層置換檢定 p = 0.489
  - 次要指標:全對率 Fisher 精確檢定 p = 1.000
  - 時間:圓桌平均約 490 秒,單人約 330 秒(約 1.5 倍)
  - 結果檔:[results/2026-09-20-ab-ollama-qwen3.8-27b-mlx.json](results/2026-09-20-ab-ollama-qwen3.8-27b-mlx.json)
- **結論:H1 不成立——量不出差別。** 同一個模型審查自己的作品,在這三題上沒有讓結果變好,多花約五成時間。
- 事後觀察(不是預先登記的分析,只當下一步的線索):
  - 圓桌沒有全對的 10 次裡,**8 次結果卡寫著「✓ 審查通過」**,只有 2 次正確標出「有未解決的問題」。也就是說,這個設定下「審查通過」只有 14/22 ≈ 64% 真的是對的——審查在給人錯誤的安心感。
  - cron 圓桌 #7:執行者撞到工具呼叫上限,留下有語法錯誤的檔案;新流程照樣送審了,審查者也讀了檔案,但照樣判「通過」。讀程式碼看不出語法錯誤,**只有真的執行才抓得到**。
  - 執行者自己寫了測試檔(test.js 等),但 API 成員只有讀寫檔案的工具,不能執行,寫了也跑不了。執行者和審查者都只能「讀」,沒有人能「跑」。
  - 單人與圓桌各有 9/24 次執行回合失敗(多半是工具呼叫往返超過 10 次),這是這個模型本身的限制,兩邊一樣。

## 實驗 5:加上自動驗證(預先登記)

實驗 3 的事後觀察指出,審查者讀完檔案照樣放行載不起來的程式。產品因此加上**自動驗證**:執行與修復之後,app 自己用語法檢查確認改動的 `.js`/`.json` 載得起來(評測的題目沒有設定驗證指令,所以只有語法檢查會生效),沒過就一定要進修復,結果也交給審查者。兩種條件都會跑驗證——它是產品行為,不是只給圓桌的加分。

**假設 H2a**(跨版本):加上自動驗證後,**單人**的測試通過比例高於實驗 3 的單人。
**假設 H2b**(同一次實驗內):加上自動驗證後,**圓桌**的測試通過比例高於單人。

> **第一次跑的結果作廢(2026-09-20)。** 48 次跑完後檢查失敗案例時發現:語法檢查用 `process.execPath`
> 開子行程,而在 app 裡那是 Electron 不是 node,少了 `ELECTRON_RUN_AS_NODE` 就變成「用 Electron
> 執行那個檔案」。後果是**有語法錯誤的檔案被判成通過**(cron 單人 #7、#8 都是 5/23 卻顯示驗證通過),
> 而成員自己寫的測試檔被實際執行、測試失敗被誤報成「載不起來」。要測的功能根本沒有生效,
> 那 48 次量到的不是「加上自動驗證」。單元測試在純 node 底下跑看不到這個差別,
> 已補上在真的 app 裡跑的 `test/harness/scenarios/verify.ts`(順便確認語法檢查不會執行檔案)。
> 作廢的那次資料:單人全對 11/24、圓桌 13/23,兩個假設都不顯著(p = 0.62、0.41)。
>
> **重跑時的已知限制(2026-09-20 20:10 開跑)**:這段期間另一個工作階段在同一個專案加了內建終端、
> 回合失敗時的健康檢查等功能,程式與實驗 3 的版本已經不只差在自動驗證。因此
> **H2b(同一次實驗內,圓桌 vs 單人)照常成立**——兩種條件跑的是同一份程式;
> **H2a(跨版本)無法歸因**,只當參考,不下結論。

- 題目、次數、指標、判斷標準:同實驗 3(`cron`、`pathnorm`、`roman`,每題每種 8 次,分層置換檢定,α = 0.05)
- H2a 的比較對象是實驗 3 的資料:同一組題目、同一個模型、同一台機器,差別只有程式版本
- 已知的限制:跨版本比較不是隨機分派,兩次之間只有程式改動這一個已知差異,但無法排除機器狀態等未知因素
- 結果:(跑完後填)

## 實驗 6:harness 全套(預先登記)

實驗 5 只加了自動驗證,而且第一次還因為 bug 沒真的生效。這一輪把 harness 的機制一次補齊,再量:

- 交叉審查改用**乾淨的 context**(審查者看不到討論與執行過程,不續接自己的記憶,改動由提示詞直接附上)
- **測試鎖**:任務開始前就存在的測試檔在修復回合鎖住(API 成員由工具擋下,CLI 成員標記)
- **多道驗證門檻**:驗證指令一行一道,依序跑,一道沒過就停
- **專案規則**:工作目錄的 CLAUDE.md / AGENTS.md 進系統提示
- **停損**:結果卡可以把工作目錄還原到任務開始前(人工操作,不影響自動流程)
- **平行衝突**:多位成員改到同一個檔案會被指出並提醒審查者

**假設 H3**:上述機制齊備後,圓桌的測試通過比例高於單人。

- 題目、次數、指標、判斷標準:同實驗 3(`cron`、`pathnorm`、`roman`,每題每種 8 次,分層置換檢定,α = 0.05)
- 跨版本比較(與實驗 3 比)**不列入結論**:這段期間另一個工作階段也改了同一個專案(內建終端、回合失敗時的健康檢查),差距無法歸因
- 已知限制:評測題目沒有設定驗證指令,所以「多道門檻」在這一輪不會生效;真正生效的是乾淨 context、測試鎖、專案規則(題目沒有規則檔,等於不生效)與平行衝突提示
- 結果(2026-09-21 跑完,48 次,1 次 app 沒跑完不計):

  | 題目 | 單人:全對 / 測試通過 / 平均時間 | 圓桌:全對 / 測試通過 / 平均時間 |
  | --- | --- | --- |
  | cron | 6/8 · 98% · 472 秒 | 7/8 · 100% · 577 秒 |
  | pathnorm | 1/8 · 93% · 256 秒 | 0/8 · 86% · 287 秒 |
  | roman | 6/8 · 87% · 283 秒 | 6/8 · 96% · 273 秒 |
  | 合計 | 13/24(54%,95% 信賴區間 35%–72%) | 13/24(54%,35%–72%) |

  - 主要指標:圓桌 − 單人 = **+1.1 個百分點**,分層置換檢定 p = 0.968
  - 次要指標:全對率 Fisher 精確檢定 p = 1.000
  - 結果檔:[results/2026-09-21-ab-ollama-qwen3.8-27b-mlx.json](results/2026-09-21-ab-ollama-qwen3.8-27b-mlx.json)
- **結論:H3 不成立——量不出差別。** 把 harness 的機制補齊之後,同一個模型互審仍然沒有讓結果變好。
- 三輪下來的一致結果(實驗 3、5、6):**同模型互審量不出好處**。三輪的差距分別是 −3.8、+4.5、+1.1 個百分點,p 都遠大於 0.05,方向也不一致——這比「小幅有效」更像「沒有效果」。
- 還沒被排除的解釋,依我認為的可能性排序:
  1. **同一個模型的盲點重疊**:審查者看不出執行者看不出的東西。這是實驗 4(換模型審查)要回答的問題。
  2. **題目的錯多半是邏輯細節**(預發布版本規則、路徑邊界),讀程式碼不容易發現;真正能抓到的是「執行起來會壞」,而那需要測試,不是再多一次閱讀。
  3. 27B 級的本機模型當審查者的能力上限。

## 實驗 4:換一個模型審查(預先登記,開跑前需要使用者同意)

**假設 H2**:執行者一樣是 Qwen、審查者換成 Claude Code 時,圓桌的測試通過比例高於單人,而且差距大於實驗 3。

- 題目、次數、指標、判斷標準:同實驗 3(`cron`、`pathnorm`、`roman`,每題每種 8 次)
- **兩組都重跑,48 次**:原本登記的是「單人組沿用實驗 6 的 24 次」,但那個前提在
  `1b53d0e` 之後不成立了——那一版修的是自動驗證(ESM 寫法的 `.js` 被誤判、NODE_OPTIONS
  汙染),驗證結果會回頭影響要不要進修復回合,單人組也會走到。兩組不同程式版本的比較
  沒有意義,所以兩組都在同一個 commit 上重跑。
- 已知的混淆:Claude Code 不只是「另一個模型」,它是能自己讀檔、能力也更強的 CLI 成員。
  結果若變好,無法把功勞單獨歸給「換模型」。
- 作廢的那一次:2026-09-21 09:08 開跑的 2 次,是在唯讀 Claude 成員因為 `--restricted`
  每次都失敗的情況下跑的(審查者根本沒有真的審查),資料已清掉,不納入。
- **執行者開著思考**(`reasoning_effort: medium`)。前一次開跑的 4 次是在思考關閉下跑的:
  Ollama 範本原本寫死 `reasoning_effort: "none"`,實測(直接打本機端點)`none` 不產生 `reasoning`
  欄位、`low`/`medium`/`high` 都會。關掉思考的 Qwen 不是它的正常水準,拿它當執行者等於在問
  一個被自己設定壓低的問題,所以那 4 次作廢,範本改成預設開啟思考後重跑。
- 第二次也重來過:開了思考之後第一次執行就以 `Headers Timeout Error` 收場,追下去發現是
  Node 內建 fetch 寫死的 300 秒等標頭上限(見該次修正)。本機模型等第一個位元組實測要 82 秒,
  排隊就會超過,等於這個上限會隨機砍掉跑得久的回合——資料會被汙染,所以修好才重跑。
- 開跑:2026-09-21(commit 以流水帳 `eval/results/exp4.journal` 為準)
- 結果:(跑完後填)
