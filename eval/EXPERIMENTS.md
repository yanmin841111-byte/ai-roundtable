## 實驗 3:新流程、難題組(預先登記)

## 實驗 5:加上自動驗證(預先登記)

實驗 3
的事後觀察指出,審查者讀完檔案照樣放行載不起來的程式。產品因此加上**自動驗證**:執行與修復之後,app
自己用語法檢查確認改動的 `.js`/`.json`
載得起來(評測的題目沒有設定驗證指令,所以只有語法檢查會生效),沒過就一定要進修復,結果也交給審查者。兩種條件都會跑驗證——它是產品行為,不是只給圓桌的加分。

**假設 H2a**(跨版本):加上自動驗證後,**單人**的測試通過比例高於實驗 3 的單人。
**假設 H2b**(同一次實驗內):加上自動驗證後,**圓桌**的測試通過比例高於單人。

> **第一次跑的結果作廢(2026-09-20)。** 48 次跑完後檢查失敗案例時發現:語法檢查用
> `process.execPath` 開子行程,而在 app 裡那是 Electron 不是 node,少了
> `ELECTRON_RUN_AS_NODE` 就變成「用 Electron
> 執行那個檔案」。後果是**有語法錯誤的檔案被判成通過**(cron 單人 #7、#8 都是
> 5/23 卻顯示驗證通過),
> 而成員自己寫的測試檔被實際執行、測試失敗被誤報成「載不起來」。要測的功能根本沒有生效,
> 那 48 次量到的不是「加上自動驗證」。單元測試在純 node 底下跑看不到這個差別,
> 已補上在真的 app 裡跑的
> `test/harness/scenarios/verify.ts`(順便確認語法檢查不會執行檔案)。
> 作廢的那次資料:單人全對 11/24、圓桌 13/23,兩個假設都不顯著(p = 0.62、0.41)。
>
> **重跑時的已知限制(2026-09-20 20:10
> 開跑)**:這段期間另一個工作階段在同一個專案加了內建終端、
> 回合失敗時的健康檢查等功能,程式與實驗 3 的版本已經不只差在自動驗證。因此
> **H2b(同一次實驗內,圓桌 vs 單人)照常成立**——兩種條件跑的是同一份程式;
> **H2a(跨版本)無法歸因**,只當參考,不下結論。

- 題目、次數、指標、判斷標準:同實驗 3(`cron`、`pathnorm`、`roman`,每題每種 8
  次,分層置換檢定,α = 0.05)
- H2a 的比較對象是實驗 3
  的資料:同一組題目、同一個模型、同一台機器,差別只有程式版本
- 已知的限制:跨版本比較不是隨機分派,兩次之間只有程式改動這一個已知差異,但無法排除機器狀態等未知因素
- 結果:(跑完後填)

## 實驗 6:harness 全套(預先登記)

實驗 5 只加了自動驗證,而且第一次還因為 bug 沒真的生效。這一輪把 harness
的機制一次補齊,再量:

- 交叉審查改用**乾淨的
  context**(審查者看不到討論與執行過程,不續接自己的記憶,改動由提示詞直接附上)
- **測試鎖**:任務開始前就存在的測試檔在修復回合鎖住(API 成員由工具擋下,CLI
  成員標記)
- **多道驗證門檻**:驗證指令一行一道,依序跑,一道沒過就停
- **專案規則**:工作目錄的 CLAUDE.md / AGENTS.md 進系統提示
- **停損**:結果卡可以把工作目錄還原到任務開始前(人工操作,不影響自動流程)
- **平行衝突**:多位成員改到同一個檔案會被指出並提醒審查者

**假設 H3**:上述機制齊備後,圓桌的測試通過比例高於單人。

- 題目、次數、指標、判斷標準:同實驗 3(`cron`、`pathnorm`、`roman`,每題每種 8
  次,分層置換檢定,α = 0.05)
- 跨版本比較(與實驗 3
  比)**不列入結論**:這段期間另一個工作階段也改了同一個專案(內建終端、回合失敗時的健康檢查),差距無法歸因
- 已知限制:評測題目沒有設定驗證指令,所以「多道門檻」在這一輪不會生效;真正生效的是乾淨
  context、測試鎖、專案規則(題目沒有規則檔,等於不生效)與平行衝突提示
- 結果(2026-09-21 跑完,48 次,1 次 app 沒跑完不計):

  | 題目     | 單人:全對 / 測試通過 / 平均時間 | 圓桌:全對 / 測試通過 / 平均時間 |
  | -------- | ------------------------------- | ------------------------------- |
  | cron     | 6/8 · 98% · 472 秒              | 7/8 · 100% · 577 秒             |
  | pathnorm | 1/8 · 93% · 256 秒              | 0/8 · 86% · 287 秒              |
  | roman    | 6/8 · 87% · 283 秒              | 6/8 · 96% · 273 秒              |
  | 合計     | 13/24(54%,95% 信賴區間 35%–72%) | 13/24(54%,35%–72%)              |
  - 主要指標:圓桌 − 單人 = **+1.1 個百分點**,分層置換檢定 p = 0.968
  - 次要指標:全對率 Fisher 精確檢定 p = 1.000
  - 結果檔:[results/2026-09-21-ab-ollama-qwen3.8-27b-mlx.json](results/2026-09-21-ab-ollama-qwen3.8-27b-mlx.json)

- **結論:H3 不成立——量不出差別。** 把 harness
  的機制補齊之後,同一個模型互審仍然沒有讓結果變好。
- 三輪下來的一致結果(實驗 3、5、6):**同模型互審量不出好處**。三輪的差距分別是
  −3.8、+4.5、+1.1 個百分點,p 都遠大於
  0.05,方向也不一致——這比「小幅有效」更像「沒有效果」。
- 還沒被排除的解釋,依我認為的可能性排序:
  1. **同一個模型的盲點重疊**:審查者看不出執行者看不出的東西。這是實驗
     4(換模型審查)要回答的問題。
  2. **題目的錯多半是邏輯細節**(預發布版本規則、路徑邊界),讀程式碼不容易發現;真正能抓到的是「執行起來會壞」,而那需要測試,不是再多一次閱讀。
  3. 27B 級的本機模型當審查者的能力上限。

## 實驗 4:換一個模型審查(預先登記,開跑前需要使用者同意)

  汙染),驗證結果會回頭影響要不要進修復回合,單人組也會走到。兩組不同程式版本的比較
  沒有意義,所以兩組都在同一個 commit 上重跑。

  秒上限把回合從中間砍斷,留下寫到一半的檔案,不是串流工具

## 題目來源與選題(2026-09-21 更新)

開了思考之後,原本的難題組對 27B 本機模型變簡單了:`cron` 單人一次就 23/23。
單人組碰到天花板時,這個實驗在數學上就量不到東西——審查者再強也只能持平。
選題標準不變:**單人大約一半做得對**,那裡才有可測的空間。

因此題庫改成兩個來源:

- **自己出的題**(`eval/ab-tasks.ts`):好處是模型沒看過(不會是訓練資料),
  壞處是難度靠猜,而且測試是我們自己寫的——對規格的誤解會同時進到題目與測試裡。
- **Exercism 官方標準測資**(`eval/ab-tasks-exercism.ts`,MIT):測資不是我們寫的,
  邊界案例是社群累積的,難度多人校準過。**已知弱點:這些題目在網路上到處都是,
  模型很可能看過解法**,所以能不能用要看實測的單人通過率,不能用「聽起來很難」決定。

兩邊都用同一道關卡把關(`test/eval.test.ts`):參考解必須全過、常見錯解必須至少錯一項。
新加的兩題:`book-store`(18 個案例,常見錯解 13/18)、`dominoes`(13 個案例,常見錯解
9/13)。

## 實驗 3、5、6 的結論作廢(2026-09-21)

那三輪的結論是「同一個模型互相審查,量不到準確率的好處」。現在知道那個結論沒有意義:
**修復回合從來沒有拿到檔案工具**(`orchestrator.ts` 的修復回合少傳了
`fileToolsEnabled`), 所以執行者是 API 成員(Ollama、各家雲端

也就是說:審查照跑、意見照給、修復回合照跑,**但治療本身是空的**。量不到差別是必然的,
跟「審查有沒有用」無關。CLI 成員(Claude

這一條和 `--restricted`

唯獨中間那一步實際上什麼都沒做,而畫面上看不出來。找到它的方式也一樣——把真正的產出攤開來看
(這次是一份修復回合「已經修好」但內容一字未改的檔案)。

修正後這三輪要重跑才有結論可言。實驗 4 的資料在修正前只有 2 次,一併作廢。
